## Какво представлява CLI


`chloros-cli` е интерфейсът от командния ред към същия процесиращ двигател, който използва и настолното приложение на Chloros
. Това е опростен HTTP
-клиент, свързан с бекенда на Chloros
(локален сървър на `127.0.0.1:5000`) — повечето команди стартират бекенда автоматично, така че един-единствен `chloros-cli process …` извикване е всичко, от което се нуждае един скрипт. След това бекендът продължава да работи за следващата команда: той спира при `chloros-cli logout` (освен ако приложението е отворено или тече изпълнение или компилация), при `chloros-cli backend stop` или сам след 30 минути без клиент, изпълнение или свързано устройство. `chloros-cli backend status` го показва.

Работи на **Windows
10/11 (x64)**и**Linux
(x86_64, както и NVIDIA Jetson arm64 на JetPack 6)**, във всеки терминал, без да се изисква графичен интерфейс. Проверете инсталацията си с:

```bash
chloros-cli --version    # prints "Chloros CLI 1.3.0"
```

Преглед на групите команди:

* **Обработка и акаунт** — `process`, `login`, `logout`, `status`, `export-status`, `language` (38 езика — вижте [Поддържани езици](supported-languages.md)), `set-project-folder` / `get-project-folder` / `reset-project-folder`, `selftest`, `update` (само за Linux
/Jetson)
* **Активен хардуер** — `lattice` (управление на камера LATTICE, над 45 подкоманди), `daq pool-*` (светлинни сензори DAQ), `time-sync` (PTP)
* **Автоматизация** — `project` (изпълнение на запазен проект в Chloros
без графичен интерфейс, включително рецепти за запис в YAML)

Глобални опции, които си струва да знаете: `--port N` (порт на бекенда, по подразбиране `5000`), `-v/--verbose`, `--restart` (принудително рестартиране на бекенда), `--backend-exe PATH`. Вижте [Справочника за CLI
](reference/cli-reference.md) за пълния списък.

## Инсталиране

CLI
**се доставя в инсталатора на Chloros** за всяка платформа — няма отделно изтегляне на CLI
. Изтеглете инсталатора от страницата [Изтегляне](download.md).

### Windows


Инсталаторът поставя CLI
в:

```

C:\Program Files\Chloros\cli\chloros-cli.exe
```

и добавя тази папка към вашата система `PATH` еднократно (актуализацията също премахва дублиращите се записи, оставени от по-ранни инсталатори) — **отворете нов терминал**след инсталирането, за да се зареди актуализираният `PATH`. Инсталаторът също така поставя скриптове за стартиране (`Chloros_CLI.bat` / `Chloros_CLI.ps1`) в кореновата директория на инсталацията, както и**Chloros
CLI
** в менюто „Старт“, като всеки от тях отваря терминал с `chloros-cli`, готов за употреба.

### Linux


Инсталирайте `.deb` за вашата архитектура с `apt` (а не `dpkg -i`, който пропуска препоръчаните изисквания на Python
SDK
):

```bash
# Linux x86_64
sudo apt install ./chloros_1.3.0_amd64.deb

# NVIDIA Jetson (arm64, JetPack 6)
sudo apt install ./chloros_1.3.0_arm64_jp6.deb
```

Това инсталира `chloros-cli` до `/usr/bin/chloros-cli` (вече на `PATH`), бекенда и програмите за командния ред (CLI
), разпакетирани в `/usr/lib/chloros/backend/` и `/usr/lib/chloros/cli/` (`/usr/lib/chloros/chloros-backend` е стартиращ модул, който стартира бекенда), средата за изпълнение на Arena SDK
, необходима на бекенда за камери LATTICE, и Python
SDK
за системата `python3`. Вижте [Инсталиране на Linux
](linux/linux-installation.md) за подробности.

### Проверка

```bash
chloros-cli --version    # "Chloros CLI 1.3.0"
chloros-cli selftest     # 7-step diagnostic: backend, API, GPU/CUDA, denoiser models
chloros-cli status       # license tier + logged-in user
```

## Вход и лицензиране

Достъпът до CLI
(и Python
SDK
) изисква **платен план Chloros
+**— всеки платен план го включва; безплатният план не го включва. Ограничението се налага**от страна на сървъра** от бекенда, а не от бинарния файл на CLI
: повикване без вход в системата се отхвърля с `401 AUTH_REQUIRED`, а заявката при влизане в безплатния план — с кода `403 PLAN_UPGRADE_REQUIRED`, независимо дали идва от `chloros-cli`, SDK
или ръчно създаден HTTP
клиент. Направете ъпгрейд на [https://cloud.mapir.camera/pricing](https://cloud.mapir.camera/pricing).

Влизайте **веднъж на всяка машина**:

```bash
chloros-cli login user@example.com 'YourPassword'
chloros-cli status
```

{% hint style="warning" %}
**Пароли със специални символи**(`$`, `!`, spaces): wrap the password in**single quotes**, as shown above. In PowerShell double quotes, `$$` се изкривява от командния интерпретатор (CLI
го открива при код 401 и автоматично прави повторен опит, но единичните кавички избягват проблема напълно).
{% endhint %}

Сесията се запазва в кеша като `~/.chloros/user_session.json` и продължава да работи офлайн през гратисния период на плана (30 дни за месечните планове, до изтичане на валидността за годишните). `chloros-cli status` работи дори без платен план, така че причината за отказа винаги е видима.

{% hint style="danger" %}
**Планирате работа без графичен интерфейс? Първо влезте в системата.**Командите за стартиране на бекенд процеси (`process`, `status`, `export-status`, …) изпълнена**без кеширана сесия**не дава бърз отказ — тя преминава в интерактивен прозорец `Email:` / `Password:` на stdin. Поради това автоматизирана cron задача или CI стъпка ще**зависне в очакване на входни данни**. Изпълнете `chloros-cli login EMAIL 'PASSWORD'` веднъж на машината, преди да планирате каквото и да било.
{% endhint %}

## Първото ви изпълнение на обработката

Насочете `process` към папка със заснети данни — той автоматично открива Survey3
(`.raw` + `.jpg`), LATTICE (`.tif`/`.tiff`), `.dng` или комбинация от тях:

```bash
chloros-cli process "C:\Images\flight_001"          # Windows
chloros-cli process ~/images/flight_001              # Linux
```

Потоците на напредъка се извеждат на живо за всеки поток на тръбопровода (откриване, анализ, обработка, експортиране), а успешното изпълнение приключва с отчитане на броя на записаните изображения: `Image products written: N`, последвано от `(plus M clamp masks)`, когато при изпълнението са записани и [clamp masks](output-image-formats.md#clamp-masks) (те не се броят като продукти).

<!-- SCREENSHOT-NEEDED: terminal capture of a `chloros-cli process` run on a LATTICE captures folder completing successfully — per-thread progress lines visible and the final "Image products written: N (plus M clamp masks)" summary line -->


Ако вече работи бекенд на Chloros
(например този на настолното приложение), `process` го използва и отваря проекта си в него. Той отказва, докато приложението е отворено върху проект, който приложението е отворило: изпълнете процеса от приложението или затворете този проект. Ако предишно изпълнение все още не е приключило, чака до 15 секунди, преди да откаже. `--restart` принудително стартира нов бекенд. В Linux
бекендът, изпълняван като услуга на systemd, никога не се рестартира: `process` го използва такъв, какъвто е, и там, където иначе би го рестартирал (`--restart` или импорт, който не е намерил нищо), извежда `sudo systemctl restart <unit>` и излиза от `1`.

### Къде се записват резултатите

`process` записва в **папка на проекта**, а не във вашата папка за входни данни:

* Без `-o`: проектът се създава във вашата папка по подразбиране за проекти (споделена с графичния интерфейс; управлявайте я с `get-project-folder` / `set-project-folder`; когато не е зададена такава, `Documents/MAPIR/Chloros Projects` във вашата потребителска папка), кръстен с `-n/--project-name` или с времева марка (`YYYYMMDD_HHMMSS`), когато е пропуснат.
* При `-o PATH`: тази папка **е** папката на проекта. Ако тя вече съдържа `project.json`, вместо да се презапише, се създава `_1`/`_2`… вместо да се презапише. Относителният `PATH` се определя спрямо папката, от която стартирате `chloros-cli`.

{% hint style="info" %}
**Относителни пътища (променени във версия 1.3.0).** Всеки път, който бекендът отваря — `-o`/`--output` при всяка команда (включително стандартната `output` на командите за запис), `--input`, `--burst-dir`, `--profile`, `--save` и `--mask` — се разрешава спрямо папката, от която стартирате `chloros-cli`, така че `-o captures/` записва в `<current folder>/captures/`. В версия 1.2.0 бекендът ги преобразуваше в собствената си инсталационна папка, което водеше до грешка „Достъпът е отказан“. При отдалечен бекенд (`CHLOROS_BACKEND_URL`) пътеките се изпращат така, както са въведени, и се преобразуват на съответната машина.
{% endhint %}

{% hint style="warning" %}
**Windows
: поддържайте папката на проекта кратка, освен ако дългите пътища не са активирани.** Когато дългите пътища в Windows
са изключени (по подразбиране в Windows
), никой файлов път не може да бъде по-дълъг от 260 символа, а продуктите се намират до около 130 символа под папката на проекта. `process` проверява това преди да започне: папка на проекта, която е прекалено дълбока, се отхвърля с **„Папката на проекта е прекалено дълбока за този компютър“**, показва се най-дългата папка на проекта, която се побира, и как да активирате дългите пътища — нищо не се обработва. Използвайте по-къса версия на `-o` (или `set-project-folder`) или активирайте дългите пътища на Windows
(опцията на инсталатора **Enable Windows
long paths**, отбелязана по подразбиране) и рестартирайте Chloros
.
{% endhint %}

В рамките на проекта продуктите са групирани **по камера, а след това по файлов формат**:

```
<project>/
├── project.json
├── calibration_data.json
└── LATT-M3M-L41-F550/                  # one folder per camera model+lens+filter
    ├── tiff16/
    │   ├── Reflectance_Calibrated_Images/
    │   ├── Debayered_Images/
    │   ├── Preview_Images/
    │   └── NDVI_Index_Images/           # one folder per requested index
    └── tiff32/
        └── Radiance_Images/             # float32 radiance always lands here
```

Папката на камерата е `LATT-<sensor>-<lens>-F<filter>` за LATTICE (съответстваща на EXIF данните на заснетата снимка `Model`) и `<model>_<filter>` (например `Survey3N_RGN`) за Survey3
. Папката за формат следва `--format`: `tiff16`, `tiff8`, `png8`, `jpg8` или `tiff32` за `TIFF (32-bit, Percent)`.

При мултиспектрална камера M3C в папката с формати може да се появи и папка `clamp_masks/`, наред с папките с продукти (например `tiff16/clamp_masks/Reflectance_Calibrated_Images/` и `tiff32/clamp_masks/Radiance_Images/`). Тя съдържа маските на пиксел за продуктите за радиантност и отражателна способност, при които разделянето на лентите е ограничило отрицателните стойности до нула — вижте [Маски за ограничаване](output-image-formats.md#clamp-masks). Никоя папка с продукти не съдържа маска.

{% hint style="info" %}
**Всеки експортиран продукт запазва името на изходния файл.**Експортираният радианс от `capture_..._raw.tif` все още се нарича `capture_..._raw.tif` — просто се намира в `tiff32/Radiance_Images/`.**Папката идентифицира продукта, а не името на файла**, затова използвайте глобален шаблон за директорията, а не за суфикса `*radiance*`.
{% endhint %}

### Опциите, които действително ще използвате

| Флаг | По подразбиране | Какво прави |
| --- | --- | --- |
| `-o, --output PATH` | папка по подразбиране за проекта | Местоположение на папката на проекта (вижте по-горе). |
| `-n, --project-name NAME` | времева марка | Име на проекта. |
| `--format FMT` | `TIFF (16-bit)` | Едно от `TIFF (16-bit)`, `TIFF (8-bit)`, `TIFF (32-bit, Percent)`, `PNG (8-bit)`, `JPG (8-bit)`. Chloros
не увеличава резолюцията: при всички 8-битови изображения по-дълбок формат се записва като `TIFF (8-bit)`, и това се посочва само веднъж. |
| `--indices NAME [NAME ...]` | няма | Индекси на растителността за експортиране (вижте [Индекси на растителността](#vegetation-indices)). |
| `--debayer {standard,texture-aware}` | `standard` | `texture-aware` = невронен дебайер, по-бавен, най-високо качество (Chloros
+, изисква CUDA GPU: без такъв се използва `standard`; отхвърля се за LATTICE заснемания, които винаги получават `standard`). |
| `--vignette / --no-vignette` | включено | Корекция на винетирането. |
| `--reflectance / --no-reflectance` | включено | Калибриране на отражателната способност; за LATTICE това е и превключвател за продукта на отражателната способност. |
| `--input-level {auto,raw,debayered,processed}` | `auto` | Налагане на входната точка на конвейера за TIFF файлове на LATTICE. |

За всичко останало — настройка на откриването на цели, PPK, пинове за експозиция, флагове за подреждане на масиви — вижте [раздела `process` от Справочника за CLI
](reference/cli-reference.md).

## Избор на това, което да се експортира (продукти на LATTICE)

Обработката на LATTICE се разпределя към **всеки приложим продукт в един цикъл**. Четирите превключвателя за всеки продукт са**включени по подразбиране**; използвайте формата `--no-`, за да изключите един от тях:

| Превключвател | Продукт |
| --- | --- |
| `--debayered` | Линеен демозаик → `Debayered_Images/`: премахване на тъмния офсет от калибрационния пакет, след което демозаика с отчитане на ръбовете, без корекция на линейността, плоско поле или размикс — същият файл, който заснемането запазва на нивото си `debayered`. Запазва се оригиналната ориентация на сензора (записана в XMP). |
| `--preview` | Предварителен преглед на екрана (баланс на бялото + гама; разтягане с фалшиви цветове за мултиспектрални изображения) → `Preview_Images/` |
| `--radiance` | float32 радиантност, W/m²/sr/nm → `Radiance_Images/` (винаги `tiff32/`) |
| `--reflectance` | uint16 отражателна способност, готова за Pix4D → `Reflectance_Calibrated_Images/` |

RGB
-камерите винаги излъчват само данни след дебайериране + предварителен преглед — радиантността/отражателността по отделни ленти няма смисъл за широколентов сензор, така че тези превключватели за тях са бездействащи. Survey3
`.raw` игнорира превключвателите и следва стандартния път за отражателност/целеви път.

```bash
# Radiance only — no DAQ downwelling needed
chloros-cli process ~/captures/lattice_flight --no-debayered --no-preview --no-reflectance
```

**`--reflectance-source {auto,target,daq}`** (по подразбиране `auto`) избира референцията за отражателната способност: `auto` прави преминалата QA [калибрационна цел](calibration-targets.md) в кадъра абсолютна референция и при липса на цел използва разделянето на светлинния сензор на DAQ за низходяща светлина (ρ = π·L/E), когато няма цел (цел, която е преминала QA с флаг, се съревновава с DAQ по измерена оценка); `target` е строг (без заместване от DAQ); `daq` се основава на DAQ. Сканиранията на измерваните цели за единица могат да се предоставят с `--target-reflectance-dir`.

{% hint style="info" %}
**Четене на пиксели на отражателната способност:**DN със значение ρ = 1,0 е**за всеки източник** — файловете LATTICE поставят `Chloros:PixelScale=32768` в XMP; Файловете Survey3
използват 65535 и не съдържат таг `Chloros:PixelScale` (но съдържат други тагове за обработка `Chloros:*`). Прочетете етикета и разделете на него, вместо да приемате, че стойността е константа. Подробностите и единственият умишлено изключен крайен случай без мащаб са описани в [Справочник за CLI
](reference/cli-reference.md).
{% endhint %}

**Обработката винаги започва от `raw`.** Производните продукти (експортирани данни за дебайериране/лъчистост/отражателност) никога не се връщат обратно в процеса — повторното им импортиране и обработка би довело до двойно прилагане на калибрационните изчисления, затова Chloros
ги пропуска и ви уведомява за това. `--input-level` е преднамерено „аварийно изходно отверстие“, когато наистина се налага да се наложи начална точка.

## Когато изпълнението се провали

От версия 1.2.0 нататък `process` отчита явно неуспех, вместо да „успее“ без да покаже нищо:

* Изпълнение, което **е поискало продукти, но не е записало нито един**— само `project.json` и `calibration_data.json` — извежда `Processing finished but wrote no image products.` и**излиза с резултат, различен от нула**, така че скриптовете могат да го засекат. Обичайните причини: входната папка не е била разпозната като заснета (проверете оформлението и `--input-level`) или всеки поискан продукт е бил неприложим за тези камери (например, искане на радиантност/отражателност от камери, които записват само RGB
).
* **Умишлено изпълнение само с метаданни** (всички продукти са изключени, без `--indices`) все пак се счита за успешно — празен изход на изображението е правилният резултат в този случай.
* Изпълнете отново с `--verbose` и проверете лога на бекенда за редове `[LATTICE-EXPORT]` / `[EXPORT-CHECK]`, които обясняват пропуските за всяка камера.
* В Windows
, когато дългите пътища са деактивирани, проектна папка, която е прекалено дълбока за ограничението от 260 символа за пътя, се отхвърля **преди** да започне обработката, като се използва най-дългата проектна папка, която се побира (вижте [Къде се съхраняват изходните файлове](#where-the-outputs-land)).
* Командите за запис (`lattice capture`, `lattice array-capture` и другите групи команди за запис) изброяват всеки файл, който не са успели да запишат, и излизат с код `1`; повтарящите се записи спират, когато устройството е пълно.

Кодове за изход: `0` успех · `1` обща грешка · `2` грешка в аргумента · `130` прекъснато с Ctrl+C.

## Индекси на растителността

Изпълнете `--indices` с едно или повече имена на предварителни настройки; всеки индекс се запазва в собствена папка `<INDEX>_Index_Images/`:

```bash
chloros-cli process ~/images/flight_001 --indices NDVI GNDVI OSAVI
```

22-те предварително зададени имена, които `process --indices` приема:

`NDVI` `GNDVI` `NDRE` `OSAVI` `SAVI` `MSAVI2` `EVI` `MSR` `TDVI` `LAI` `GCI` `GRVI` `GSAVI` `GOSAVI` `NLI` `MNLI` `RDVI` `WDRVI` `CVI` `ENDVI` `GLI` `VARI`

Към проекта се добавя име, което все още не фигурира в списъка му. Име, което не е предварително зададено или което камерите не могат да създадат, се пропуска с предупреждение, посочващо го. Ако CLI
-то не може да прочете текущия индексен списък на проекта, то оставя списъка непроменен и извежда предупреждение, вместо да го замени.

{% hint style="warning" %}
**Съществуват три индексни списъка — не ги бъркайте.**Падащото меню „Настройки на проекта“ в графичния интерфейс съдържа 27 формули (добавя `FCI1`, `FCI2`, `GARI`, `GEMI`, `LCI` — тези пет са само за графичния интерфейс и**не** са валидни за `--indices`). Командата за режим на живо/офлайн `lattice index --preset` използва свой собствен списък с 22 предварителни настройки. Формулите и математическите изчисления за честотните ленти са документирани в [Формули за мултиспектрални индекси](project-settings/multispectral-index-formulas.md).
{% endhint %}

## Светлинни сензори DAQ: Кратък преглед

Серията `daq pool-*` управлява спектралните сензори за събиране на данни (MAPIR
) на DAQ (DAQ-U през USB, DAQ-M през BLE, DAQ-E през Ethernet) чрез постоянния пул на бекенда — GUI, CLI
и SDK
споделят един и същ дескриптор в режим на реално време. **`pool-*` е поддържаният DAQ път в доставения CLI
**; другите подкоманди на `daq`, към които може да видите препратки, представляват вътрешен за MAPIR
интерфейс, предназначен само за източници, и при излизане от тях се получава явна грешка, насочваща ви към `pool-*`.

```bash
# 1. Open a pooled session (pick the line matching your sensor)
chloros-cli daq pool-connect                              # smart-detect
chloros-cli daq pool-connect --port COM3                  # DAQ-U on a specific COM port
chloros-cli daq pool-connect --mac AA:BB:CC:DD:EE:FF      # DAQ-M by BLE MAC
chloros-cli daq pool-connect --eth-host daq-e-xxx.local   # DAQ-E by hostname (reliable)

# 2. List pooled sensors and their ids
#    (DAQ-U ids look like 'CB-7C-A8-2E-5F'; DAQ-E ids like 'daq-e-def330')
chloros-cli daq pool-list

# 3. Read the latest calibrated spectrum (W/m²/nm)
chloros-cli daq pool-latest --sensor-id CB-7C-A8-2E-5F

# 4. Record a calibrated .daq file for 60 s
chloros-cli daq pool-record --sensor-id CB-7C-A8-2E-5F --duration 60 \
  -o ~/Documents/spectra --device-name "field-A"

# 5. Release
chloros-cli daq pool-disconnect --sensor-id CB-7C-A8-2E-5F
```

`pool-record` без `--duration` работи до `pool-record --stop`; директорията по подразбиране за изходните данни е `~/Documents/DAQ Live View/` **на машината на бекенда**. Профилът за корекция на капацитета се избира при свързване (`--cap-id`, подразбиращ се за бекенда `sunshine_cosine`) и може да бъде сменян на живо с `pool-set-cap` — профилите за капацитет и калибрираният обхват на сензора са разгледани в главите за DAQ в настоящото ръководство.

{% hint style="warning" %}
**DAQ-E на хост с няколко мрежови карти:** първото автоматично откриване на `pool-connect --eth` след стартиране може да се провали дори при изправен сензор. `--eth-host <ip-or-hostname>` е надеждната опция — използвайте я винаги, когато откриването не даде резултат.
{% endhint %}

## Камери LATTICE, PTP и автоматизация на проекти

Серията `lattice` (над 45 подкоманди) обхваща цялостната работа с камери LATTICE: откриване, единични заснемания, постоянни синхронизирани масиви с потока за интелигентна подготовка на GUI, преглед на живо в браузъра, подреждане, индексни изчисления и диагностика на хост-NIC. Ето един пример:

```bash
chloros-cli lattice info                                          # discover cameras
chloros-cli lattice capture -o output/                            # one frame, all export types
chloros-cli lattice array-connect --serials SN1,SN2,SN3,SN4       # persistent synced array
chloros-cli lattice array-capture --processing reflectance -o out/
```

Наред с това: `chloros-cli time-sync` предоставя информация за PTP „grandmaster“, който хостът Chloros
изпълнява (камерите LATTICE и сензорите DAQ-E работят като „slave“ към него за синхронизиране на времевите отметки между устройствата), а `chloros-cli project` отваря запазен проект на Chloros
и управлява камерите, масивите и сензорите му без графичен интерфейс — включително скриптови YAML рецепти за заснемане.

Тези три групи (`lattice`, `project`, `daq pool-*`) са и единствените, които поддържат `CHLOROS_BACKEND_URL` за управление на **отдалечен** бекенд; основните команди винаги са насочени към локалната машина.

Пълни постъпкови ръководства можете да намерите в главите за LATTICE на това ръководство; всеки флаг е описан в [Справочник за CLI
](reference/cli-reference.md).

## Отстраняване на проблеми: Топ 5

| Симптом | Решение |
| --- | --- |
| `Login required` или планирана задача зацикля на подканата `Email:` | Изпълнете `chloros-cli login EMAIL 'PASSWORD'` веднъж на тази машина — команди без кеширана сесия се изпълняват интерактивно, вместо да дават грешка веднага. |
| `backend unreachable` | Стартирайте десктоп приложението Chloros
или стартирайте бекенда ръчно: `"C:\Program Files\Chloros\backend\chloros-backend.exe"` на Windows
(папката `backend` във вашата инсталационна папка; тя не се намира в `PATH`), `chloros-backend` под Linux
. `chloros-cli backend status` показва дали някой се изпълнява; `lattice`/`project`/`daq pool-*` никога не стартират такъв. Ако ги насочите към отдалечен бекенд, проверете `CHLOROS_BACKEND_URL`. |
| Свързването с масива е блокирано: `FRAMES WILL DROP` / `Reduce ROI to enable` | Пръстенът за приемане на мрежовата карта на хоста е възстановен към заводските настройки — това е най-честата причина за отказ на свързване на система, която преди това е работила, обикновено след актуализация на драйвера на мрежовата карта. Изпълнете `chloros-cli lattice network --fix` от терминал с **повишени права** (или задайте `ReceiveBufferLen=256`, `PendingReceives=64`); вижте раздела *Настройка и оптимизация на мрежовата карта на хоста* в справочника. |
| Подкомандата `daq` излиза с съобщение: „изисква пълния DAQ пакет…“ | Използвайте командите `daq pool-*`, които управляват същия сензор чрез бекенда: свързване, поточно предаване, запис, избор на капацитет, а за DAQ-E — мрежовите му настройки, рестартиране и актуализации на фърмуера (или `chloros_sdk.connect_daq_sensor()` от Python
). |
| Jetson извежда предупреждение за суап преди големи папки | Добавете суап, поддържан от файл — CLI
извежда точните команди `fallocate`/`swapon`, които трябва да се изпълнят. |
