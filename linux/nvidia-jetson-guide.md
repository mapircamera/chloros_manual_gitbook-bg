# Ръководство за NVIDIA Jetson

Chloros
на NVIDIA Jetson позволява мултиспектрална обработка на изображения в периферията — на терен, на безпилотни летателни апарати (UAV) и в отдалечени инсталации. Chloros
1.3.0 разпознава вашия модел Jetson при стартиране и оптимизира стратегията за обработка според открития хардуер. **Не се изисква ръчна настройка.**
{% hint style="info" %}
**Пакетът за Jetson 1.3.0 извършва обработката на графичния процесор (GPU) на Jetson.** `chloros_1.3.0_arm64_jp6.deb` е създаден за JetPack 6 и използва CUDA версията на PyTorch от JetPack 6, така че обработката, включително алгоритъмът за дебайеризация Texture Aware, се изпълнява на графичния процесор на Orin. Пакетът не съдържа CUDA: той използва библиотеките CUDA и cuDNN, които JetPack 6 инсталира (`sudo apt install nvidia-jetpack` на образ, в който те липсват). Когато не може да се използва CUDA GPU, обработката се изпълнява на CPU, а Texture Aware използва стандартния дебайер.
{% endhint %}

## Инсталиране

```bash
# Install the arm64 .deb package (JetPack 6) -- apt, not dpkg -i, so the
# Python SDK's requirements (python3-numpy, python3-requests) come too
sudo apt install ./chloros_1.3.0_arm64_jp6.deb

# Verify installation
chloros-cli --version    # prints "Chloros CLI 1.3.0"
python3 -c "import chloros_sdk; print(chloros_sdk.__version__)"   # the .deb installs the SDK

# Run system diagnostics
chloros-cli selftest
```

`.deb` инсталира Python
SDK
за системата `python3`, съответстващ на тази версия. Само в virtualenv трябва да се инсталира включеният в пакета wheel файл: `pip install /usr/lib/chloros/sdk/chloros_sdk-*.whl` (изцяло офлайн). За общи подробности относно инсталацията в Linux
, местоположенията на файловете и отстраняването на проблеми вижте [Инсталация в Linux
](linux-installation.md).

{% hint style="info" %}
**Няма повече разпаковане при стартиране.** От версия 1.3.0 нататък бекендът и CLI
-то се инсталират в разпакован вид в `/usr/lib/chloros/`, така че вече не се разпаковат във временна директория при всяко стартиране. Временните файлове все още се записват автоматично в `/mnt/ssd/tmp`, когато тази папка съществува; в противен случай можете да зададете `TMPDIR` като път към вашия NVMe (`export TMPDIR=/mnt/nvme/tmp`).
{% endhint %}

## Динамична адаптация на изчислителната мощност на Jetson

### Как работи

При стартиране Chloros
създава профил на вашата система:

1. **Открива модела на Jetson** чрез `/proc/device-tree/model`
2. **Прочита наличната споделена памет на GPU/CPU** (Jetson използва унифицирана памет)
3. **Пита PyTorch дали може да използва CUDA** — ако са инсталирани CUDA и cuDNN от JetPack 6, това е възможно
4. **Избира стратегия за обработка** (`GPU_PARALLEL`, `GPU_SINGLE` или `CPU_PARALLEL`) и броя на работните процеси автоматично

Решението се определя от **общия обем на споделената RAM**, а не от името на модела:

* **При обща RAM под 12 GB**(всички Jetson с 8 GB):**1 работник — целенасочена последователна обработка**. Паметта е твърде ограничена за едновременна работа на няколко работници, затова изображенията се обработват едно по едно. При Jetson модели с**8 GB или по-малко**, Thread 3 изцяло пропуска пула от работници и изпълнява работата си за всеки образ в рамките на самия процес. В лога на бекенда тази стратегия е обозначена като `GPU_SINGLE`.
* **12 GB или повече**(Orin NX 16 GB, AGX Orin): обединената памет отговаря на изискванията за `GPU_PARALLEL`, но броят на работниците е**ограничен до 2 на Jetson** — графичният процесор, RAM паметта на работните процеси и CUDA контекстите за всеки работник черпят от един и същ споделен пул, така че при повече работници съществува риск от грешки поради изчерпване на паметта.
* **Липса на използваема CUDA** (липсват CUDA библиотеките на JetPack): `CPU_PARALLEL` при 12 GB или повече, по един образ наведнъж по-долу.

Можете да преопределите автоматичния избор с променливата на средата `CHLOROS_STRATEGY` — вижте [Динамична адаптация на изчислителната мощност](../processing-architecture/dynamic-compute-adaptation.md#manual-strategy-override).

### Поведение за всеки модел

| Модел на Jetson                | Стратегия       | Работни процеси | Изпълнение                                      |
| --------------------------- | -------------- | ------- | ---------------------------------------------- |
| **Jetson Orin Nano 8 GB**    | `GPU_SINGLE`   | 1       | Последователен цикъл в рамките на процеса (`tiled_gpu` при недостиг на памет) |
| **Jetson Orin NX 8GB**      | `GPU_SINGLE`   | 1       | Последователна циклична обработка в рамките на процеса                     |
| **Jetson Orin NX 16 GB**     | `GPU_PARALLEL` | 2       | Паралелни работни процеси, `fused_gpu` път  |
| **Jetson AGX Orin 32–64 GB** | `GPU_PARALLEL` | 2       | Едновременни работни процеси, `fused_gpu` път  |

Основната разлика между платформите е **паметта**. Jetson с 8 GB трябва да обработва изображенията едно по едно, като използва ефективен от гледна точка на паметта подход с разделяне на изображенията на плочки при висока натовареност, докато Orin с 16 GB+ може да обработва 2 изображения едновременно чрез GPU, използвайки консолидиран конвейер с по-висока пропускателна способност.

### Бюджет на GPU за всеки модел

Всеки модел Jetson разполага и с хардуерен профил, който ограничава колко от споделения пул може да заеме обработката и мащабира размера на партидите:

| Модел | Максимален бюджет на GPU | Мултипликатор на размера на партидата | Запазено за системата/дисплея |
| --- | --- | --- | --- |
| **Jetson Orin Nano** | 70% | ×0,8 | 2,0 GB |
| **Jetson Orin NX** | 75% | ×1,0 | 3,0 GB |
| **Jetson AGX Orin** | 80% | ×1,5 | 4,0 GB |

Откритата RAM памет коригира профила: при Jetson, отчитащ **16 GB или повече**, множителят на партидата се увеличава с ×1,2. Базовият размер на партидата преди прилагане на множителите е 8 изображения.

За пълна справка относно адаптацията на изчислителната мощност вижте [Динамична адаптация на изчислителната мощност](../processing-architecture/dynamic-compute-adaptation.md).

## Ограничение на честотата на GPU за Texture Aware на Nano и Orin Nano

Дебайериращият алгоритъм „Texture Aware“ изпълнява инференция на невронна мрежа на GPU, което може да предизвика **предупреждения за претоварване по ток**при нискоенергийните модели Jetson (клас 10–15 W) при пълна тактова честота на GPU. Когато изпълните `--debayer texture-aware` на**Jetson Nano или Orin Nano**, CLI
проверява максималната честота на GPU и я ограничава до **510 MHz** (510000000), ако в момента тя е по-висока:

* Ако CLI
-ът може да запише в sysfs възела за честотата на GPU-то, ограничението се **прилага автоматично** и се извежда потвърждение.
* Ако не (изисква root права), CLI
-ът извежда точната команда `sudo` за ръчно прилагане на ограничението, изчаква за момент, за да можете да я прочетете, след което продължава — обработката все още тече, но може да се показват предупреждения за претоварване по ток.

За да приложите ограничението сами преди обработката:

```bash
echo 510000000 | sudo tee /sys/devices/platform/bus@0/17000000.gpu/devfreq/17000000.gpu/max_freq
```

Моделите с по-висока мощност (Orin NX 25W, AGX Orin 60W) работят на пълна скорост на GPU; не се прилага ограничение. Стандартният дебайер никога не задейства ограничението при нито един модел.

{% hint style="info" %}
**„Texture Aware“ на Jetson винаги обработва по едно изображение наведнъж.** Всеки работник би имал нужда от собствен CUDA контекст (~1 GB), както и от собствено копие на модела за отстраняване на шума, което обединената памет не може да си позволи — затова на Jetson пътят на Texture Aware е фиксиран към един-единствен работник със сериализиран достъп до GPU. Очаквайте Texture Aware да бъде значително по-бавен от Standard на всеки Jetson. „Texture Aware“ се прилага за изображения от Survey3
: заснетите с LATTICE винаги получават „Standard“ дебайеринг. Без използваем CUDA GPU изпълнението използва „Standard“, а бекендът записва един ред `[DEBAYER] … needs a CUDA GPU …`, в който се посочва причината (показано с `chloros-cli --verbose`).
{% endhint %}

## Термично управление

Устройствата Jetson имат ограничен термичен резерв, особено при затворени или въздушни инсталации. Chloros
следи температурата на SoC и автоматично регулира размера на партидите:

| Температура         | Действие                                            |
| ------------------- | ------------------------------------------------- |
| **&lt; 70°C**          | Нормална работа — пълна скорост на обработка          |
| **70°C** (Предупреждение) | Размерът на партидите постепенно намалява (от 100% до 50% при температура между 70°C и 80°C) |
| **80°C** (Критично) | Агресивно ограничаване (50% → 0% между 80°C и 90°C) |
| **90°C** (Изключване) | Пълно спиране на обработката на GPU — необходимо охлаждане |

{% hint style="warning" %}
**Осигурете адекватна вентилация и отвод на топлината** за продължителна обработка, особено в затворени полеви корпуси или въздушни системи. Термичното ограничаване ще намали производителността на обработката, за да защити хардуера.
{% endhint %}

## Управление на паметта

Устройствата Jetson използват **унифицирана памет** — графичният процесор (GPU) и централният процесор (CPU) споделят една и съща физическа RAM памет. Посочената VRAM (например ~15,3 GB при Orin NX 16 GB) не е специално предназначена памет за графичния процесор; това е същата RAM памет, която се използва от операционната система и всички останали процеси.

### Предупреждение и препоръки относно суап паметта

Преди обработката на Jetson, CLI
преброява RAW изображенията във вашата входна папка (`.tif`, `.tiff`, `.raw`, `.dng` — JPG прегледите не се броят), изчислява максималното количество памет, необходимо за изпълнението, и **предупреждава преди стартиране**, ако RAM + суап вероятно са недостатъчни. Предупреждението е озаглавено `LOW MEMORY WARNING - Jetson Detected`, извежда броя на изображенията, RAM, текущия swap и очакваната максимална стойност, след което дава точните команди `fallocate` / `chmod` / `mkswap` / `swapon`, съобразени с размера на вашия проект (никога по-малък от 8 GB). Програмата прави пауза от няколко секунди, за да не се изгуби съобщението при превъртане назад, след което обработката продължава.**Оценки за паметта, използвани от предупреждението:**

| Режим на дебайериране | Базов | На изображение |
| --- | --- | --- |
| Стандартен | ~1,5 GB | ~10 MB |
| С отчитане на текстури | ~2,5 GB (модел + среда за изпълнение на Python) | ~15 MB |

Предупреждението се задейства, когато прогнозираният пик надвиши RAM + суап минус 1 GB резерв за сигурност, като се отчита само суап, **подкрепен с файлове** — конфигурация, използваща само zram, все пак ще бъде маркирана.

За да добавите суап ръчно (пример: 8 GB):

```bash
# Check current memory and swap
free -h

# Create a swap file
sudo fallocate -l 8G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile

# Make persistent across reboots
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

### Обработка на OOM (Out of Memory)

По време на обработката Chloros
следи паметта на графичния процесор и плавно намалява производителността, вместо да се срине:

1. Когато използването на паметта на GPU надвиши **85%**, размерите на партидите се намаляват превантивно
2. Ако все пак възникне събитие за изчерпване на паметта, размерът на партидата се **намалява наполовина** и се намалява отново наполовина при всяко следващо OOM; всяка следваща успешна партида отменя това ограничение с една стъпка
3. При продължително натоварване конвейерът преминава от `fused_gpu` към по-ефективния по отношение на паметта път `tiled_gpu`, а като последна мярка — към обработка на CPU

Тъй като графичният процесор (GPU) споделя RAM паметта на Jetson, RAM паметта плюс суап паметта все още ограничават изпълнението — предупреждението за суап паметта по-горе е индикаторът, на който трябва да се обърне внимание.

### Препоръки за съхранение

* **NVMe SSD** се препоръчва силно за разгръщания на arm64
* SD картите са твърде бавни за обработка — използвайте ги само като носител за стартиране
* Предвидете 2–3 пъти по-голям размер на обработените данни в сравнение с размера на суровите изображения

### Работа без монитор чрез SSH


Chloros
CLI
е идеален за инсталации на Jetson без монитор:

```bash
# SSH into the Jetson
ssh user@jetson-hostname

# Process a dataset
chloros-cli process /data/datasets/flight001 --format "TIFF (32-bit, Percent)"

# Monitor export progress
chloros-cli export-status
```

### Постоянно активен бекенд за синхронизация на времето на LATTICE / DAQ-E

Ако вашият Jetson управлява камери LATTICE или светлинни сензори DAQ-E без монитор, активирайте бекенд услугата systemd **като ваш потребител**, така че PTP grandmaster да работи непрекъснато и скриптовете на SDK
да откриват работещ бекенд (устройството е инсталирано, но не е активирано по подразбиране):

```bash
sudo systemctl enable --now chloros-backend@$USER.service    # $USER expands to your user name
chloros-cli time-sync status
```

След това бекендът работи като вас: записите, които създава, са ваши, и той използва вашия `chloros-cli login`. Вижте [Инсталация на Linux
](linux-installation.md#always-on-ptp-for-headless-hosts) за подробности, включително root `chloros-backend.service` и как пакетът прави PTP портовете 319/320 достъпни за свързване без root.

### Автоматизирана обработка с systemd

Създайте услуга в systemd за автоматизирана обработка:

```ini
# /etc/systemd/system/chloros-process.service
[Unit]
Description=Chloros Automated Processing
After=network.target

[Service]
Type=oneshot
User=chloros
ExecStart=/usr/bin/chloros-cli process /data/incoming --output /data/processed
StandardOutput=append:/var/log/chloros-process.log
StandardError=append:/var/log/chloros-process.log

[Install]
WantedBy=multi-user.target
```

`chloros-cli process` излиза с не нулев код, когато изпълнение, което е поискало продукти, не запише никакви изображения, така че състоянието на неуспех в systemd е значимо за мониторинг.

Комбинирайте със таймер на systemd за планирана обработка:

```ini
# /etc/systemd/system/chloros-process.timer
[Unit]
Description=Run Chloros Processing Every Hour

[Timer]
OnCalendar=hourly
Persistent=true

[Install]
WantedBy=timers.target
```

```bash
sudo systemctl enable chloros-process.timer
sudo systemctl start chloros-process.timer
```

## Примери за работни потоци

### Основна обработка на Jetson

```bash
#!/bin/bash
# Process a drone flight dataset on Jetson
chloros-cli process /data/flights/flight_042 \
    --output /data/processed/flight_042 \
    --format "TIFF (32-bit, Percent)" \
    --indices NDVI GNDVI OSAVI
```

### Python
SDK
на Jetson

```python
from chloros_sdk import ChlorosLocal

with ChlorosLocal() as chloros:
    chloros.create_project("field_survey_042")
    chloros.import_images("/data/flights/flight_042")
    chloros.configure(
        indices=["NDVI", "GNDVI", "OSAVI"],
        export_format="TIFF (32-bit, Percent)",
        reflectance_calibration=True
    )
    chloros.process(mode="parallel")

print("Processing complete!")
```

### Пакетна обработка на множество полети

```bash
#!/bin/bash
# Process all flight datasets in a directory
for flight in /data/flights/*/; do
    name=$(basename "$flight")
    echo "Processing $name..."
    chloros-cli process "$flight" \
        --output "/data/processed/$name" \
        --format "TIFF (32-bit, Percent)" \
        --indices NDVI OSAVI
    echo "Completed $name"
done
```

## Препоръчителни системи Jetson за използване на терен

За внедряване на терен и във въздуха, имайте предвид следните варианти на носещи платки Jetson Orin NX 16GB:

* **Въздушно/дрон**: Системи с вибрационна устойчивост (MIL-STD), леки (под 300 g), с пасивно охлаждане
* **Устойчиви за полеви условия**: Водоустойчиви корпуси IP67/IP69K с възможност за свързване на PoE GigE камера
* **Минимални/икономични**: Комплекти за разработчици с допълнителни корпуси
